## 二、技术结构：它和我们的最大不同

### 1. 它没有后台、没有扩展权限

它的 `manifest.json` 非常轻：

- 没有 `permissions`；
- 没有 `background` / Service Worker；
- 没有 `downloads`、`storage`、`host_permissions`；
- 只有一条 content script，匹配 `*://*.bilibili.com/*`；
- 把 `*.js`、`*.wasm`、`*.html` 等全部设为 `web_accessible_resources`。

content script 本身只有几百字节，作用是往页面里注入一个 `<script type="module">`，加载扩展内的 `bilibili-helper-content-script.js`。真正的逻辑全部运行在 **B 站页面上下文**里。

### 2. 它靠页面上下文拿 Cookie 和 Referer

因为代码运行在 B 站页面里：

- `fetch` 自动带 B 站 Cookie；
- 自动带 B 站 Referer；
- 可以直接读页面状态、播放器状态；
- 不需要 host permissions；
- 不需要 DNR 改请求头；
- 下载用 `<a download>` + Blob，不需要 `chrome.downloads`。

代价是：

- 没有扩展的隔离边界；
- 所有资源暴露给 B 站页面；
- 逻辑容易被页面 CSP、播放器改版、XHR 拦截影响；
- 不符合我们当前“后台签名 + 独立下载页”的架构。

### 3. 它不自己请求清晰度列表，而是让用户在 B 站播放器里切换

界面文案明确写着：

> 请在页面中 B 站自己的播放器内切换清晰度

它会 hook 页面的 `XMLHttpRequest`，监听 URL 里包含 `/playurl` 的响应，拿到当前播放器请求的清晰度数据，再下载对应的视频/音频轨。

它也有一个直接请求：

```text
//api.bilibili.com/x/player/wbi/playurl
  ?qn=120&fnver=0&fnval=4048&fourk=1
  &avid=...&bvid=...&cid=...
```

注意：这个请求没有 `w_rid` / WBI 签名。可能是页面上下文 + Cookie 下接口容忍，或只是兜底路径。我们的实现是后台 WBI 签名，稳定性逻辑不同。

### 4. 它支持番剧、电影、电视剧和 FLV/durl

代码里同时处理：

- `dash`：分离的视频/音频轨；
- `durl`：FLV/MP4 分段；
- 多个视频分段、音频分段；
- `ffmpeg` 合并；
- `video_codecid` 匹配，避免选到不同编码的轨。

它的 URL 判断包括：

- `/video/(av|bv)...`：普通投稿；
- `/bangumi/play/...`：番剧；
- 页面标题/描述里明确写“番剧 电影 影视 电视剧”。

这正是它比我们当前版本覆盖更广的地方，也是它法律风险最高的地方。

### 5. 它有两套下载模式

- **高级模式**：fetch 读取进度，Blob + ffmpeg 合并，自动重命名；占用内存大；
- **兼容模式**：直接走浏览器默认下载，资源占用小，但不自动合并。

我们的当前版本是：

- 合并模式；
- 分离模式；
- 仅音频模式；
- 统一在独立下载页处理，有进度、状态和失败兜底。

体验上我们更现代；它的“兼容模式”值得借鉴，作为低内存/低权限兜底。

### 6. 它内置 ffmpeg.wasm，但实现是自写的

- 内置 `ffmpeg-core.js`、`ffmpeg-core.wasm`（约 31.6 MB）；
- 自己的 `ffmpeg.worker.js`；
- 默认 `@ffmpeg/core@0.12.1`，失败时从 `unpkg.com` 加载；
- 用 `-vcodec copy -acodec copy` 合并。

从商店政策角度看，`unpkg` 远程加载是潜在风险点；我们的 ffmpeg 完全本地打包，更干净。

### 7. UI 是注入到 B 站页面里的老式面板

- 位置在播放器下方/侧边；
- 有下载地址、日志、清晰度提示、设置；
- popup 只是教程/更新日志入口；
- 设置存 `localStorage`，没有 `chrome.storage`；
- 没有独立下载页。

我们的面板是 Shadow DOM + 现代卡片，另有独立下载页和弹窗；视觉和交互更好，但多了一次“打开下载页”的跳转。

## 四、它做得比我们好的地方

1. **覆盖范围更广**：番剧、电影、电视剧、FLV 分段，用户感知价值更高。
2. **页面内闭环**：不用打开新标签页，点击后就在当前页下载/合并。
3. **兼容模式**：低内存、低权限路径，适合老电脑/大文件。
4. **直接读取播放器状态**：不依赖自己维护清晰度列表，减少 API 适配工作。
5. **历史积累**：从 2018 年迭代到 2025 年，处理过大量页面改版和异常。
6. **商店和官网矩阵**：Chrome、Edge、CRX、ZIP、网盘、教程、更新日志、在线合并工具，转化路径完整。
7. **变现克制**：没有广告/付费墙，主要靠赞赏和好评；用户反感度低。

## 五、它做得比我们差/我们不能照搬的地方

1. **法律定位危险**：描述直接写“下载版权受限（能看不能缓存）的番剧 电影”，并已收到律师函。我们不能用这种文案，也不应把“绕过缓存限制”当卖点。
2. **权限模型粗放**：把全部资源暴露给页面，缺少隔离；一旦页面被 XSS，攻击面更大。
3. **依赖页面 hook**：播放器改版、CSP、XHR 封装变化都可能让它失效。
4. **远程 unpkg 兜底**：商店对远程代码敏感；我们应保持本地打包。
5. **UI 老旧**：信息密度高、样式老；我们的面板和下载页明显更现代。
6. **没有独立任务管理**：刷新/关闭页面会中断；我们的 `storage.session` + 下载页更稳。
7. **清晰度依赖用户先切播放器**：多一步操作，不如我们的下拉框直接。
8. **没有多站点架构**：它的代码和 B 站页面强耦合，很难扩展到抖音/TikTok。

## 六、关键结论

### 1. 需求被验证了，但品类有法律风险

竞品能上架多年，说明“B 站视频下载”有真实需求；但律师函说明平台会维权。  
**不能把公司/收入全部押在“B 站下载”上。**

### 2. 我们的技术架构更干净，但覆盖窄

- 我们：后台签名、独立下载页、WBI、DNR、现代 UI、可扩展多站点；
- 竞品：页面注入、无权限、番剧/电影/FLV、页面内闭环、历史积累。

短期我们不该盲目拼“番剧/付费内容”，而应拼：
- 普通公开视频的稳定性和体验；
- 安装/权限的透明度；
- 多站点扩展能力；
- 不碰 DRM/付费的合规定位。

### 3. 商店不是唯一出路，反而可能是风险点

竞品公告已经说明商店会下架。  
GitHub + 官网 + 社区分发更适合作为“抗下架”的底座；商店是增量，不是唯一命脉。

### 4. 变现要换思路

竞品只靠赞赏，说明：
- 个人用户付费意愿有限；
- 广告/付费墙会明显伤害体验；
- 法律风险高的品类不适合做重付费。

更稳的方向：
- 免费开源 + 赞赏；
- 付费桌面端做批量/多站点/长视频；
- B2B/白标/版权清晰的素材归档；
- 不做“付费解锁 B 站受限内容”。

## 七、建议我们借鉴/不借鉴

### 可以借鉴

- **兼容模式**：低内存时直接保存分离文件，不强制 ffmpeg；
- **页面内进度反馈**：至少让用户不用来回切换标签页；
- **FLV/durl 兜底**：如果未来覆盖老视频/番剧，可加，但先评估合规；
- **下载日志与失败提示**：我们已有，可继续优化；
- **官网矩阵**：教程、更新日志、FAQ、在线工具，提升转化；
- **赞赏入口**：轻量、不破坏体验。

### 不要照搬

- “版权受限/能看不能缓存/番剧电影都能下”的营销文案；
- 把全部扩展资源暴露给页面；
- 依赖 unpkg 远程加载核心；
- 为了覆盖番剧而绕过付费/会员限制；
- 在商店描述里使用 B 站官方商标/Logo 做背书；
- 把“下载”作为唯一商业模式。

---

## 八、下一步建议

1. **暂停 GitHub 发布动作**（当前未创建仓库、未推送代码）。
2. **先定品牌与合规边界**：
   - 商店版用中性名称；
   - 文案只写“下载你本来就能观看的公开视频”；
   - 明确不绕过会员/付费/DRM；
   - 不把番剧/电影作为主卖点。
3. **决定是否做番剧/FLV**：
   - 如果做，只做免费、可正常播放的内容，并先咨询法律意见；
   - 如果不做，就把“普通投稿视频 + 多 P + 稳定合并”做到最好。
4. **优先改进体验而不是扩权**：
   - 页面内进度/状态；
   - 低内存兼容模式；
   - 失败重试与更新提示。
5. **分发策略**：
   - GitHub Release + 官网落地页作为底座；
   - 商店能上就上，但默认接受“可能下架”；
   - 不把用户资产只放在一个商店。
6. **商业化**：
   - 先赞赏；
   - 观察批量/多站点需求；
   - 再考虑付费桌面端或 B2B；
   - 不做“付费解锁受限内容”。
